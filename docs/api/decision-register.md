# Реестр архитектурных решений и открытых вопросов — Web API v2 (C0)

> Компактный реестр к [README](README.md) и [`web-api-v2.openapi.yaml`](web-api-v2.openapi.yaml).
> **Это не подпись владельца.** Финальное ревью приняло архитектуру как *baseline*, а не как разрешение на изменения
> в production или на непроверенные миграции. Решения D1–D18 **не считаются подписанными все**: статус каждого указан ниже.
>
> Источники: [чек-лист D1–D18](https://github.com/Pickle-Pee/smm_ai_helper_web/issues/6#issuecomment-6857963100),
> [Addendum 2](https://github.com/Pickle-Pee/smm_ai_helper_web/issues/6#issuecomment-6858230970),
> [финальное ревью](https://github.com/Pickle-Pee/smm_ai_helper_web/issues/6#issuecomment-6860263535).

Статусы: 🟢 — ревью назвало решение разумным (подпись за владельцем); 🟡 — принято как baseline, ждёт подписи;
🔴 — открыто, нужен ответ.

## 2. Три замечания финального ревью

| # | Замечание | Как учтено в контракте | Что остаётся |
|---|---|---|---|
| R1 | **D3b — fork, а не единый бренд.** Не описывать общий AI-core как общее хранилище бренда; дать безопасный ручной реимпорт или явно отложить | `importTelegramBrand` описан как однонаправленная копия с `imported_from`; обязательны `expected_version` и `confirm_overwrite: true`; повторный импорт закрыт флагом `WEB_BRAND_REIMPORT_ENABLED` | 🔴 OQ-1: продуктовое решение о ручной повторной синхронизации и тексте в UI |
| R2 | **D11 — не завышать атомарность отзыва.** Вторая проверка не гарантирует, что ни один ответ после коммита отзыва не содержит данных | Формулировка в `getMessage`, `submitMessage` и README §7.3: «доступ проверяется непосредственно перед формированием ответа; последующие запросы отклоняются»; линеаризуемость явно не обещается | Тесты O-T1…O-T5 с реалистичными утверждениями — в B5; протокол блокировок — только если потребуется строгая гарантия |
| R3 | **B9 — конкурентность веб-чата и триггер purge.** Receipt по ключу не сериализует разные запросы треда; триггер — не граница авторизации | Единственный in-flight слот на тред (`thread_busy`) уже для Copilot-тредов; для чата дополнительно `expected_last_seq` (`stale_thread`); восстановление без повторного вызова модели; транзакции не держатся на время вызова модели. Триггер описан как соглашение о целостности | 🔴 OQ-11: ограниченная роль БД для purge; тесты одновременных вкладок — в B9 |

## 3. Решения, принятые в C0 (требуют подтверждения)

Уточнения и отступления от таблицы API из Addendum 1 §4, сделанные при фиксации контракта.

| # | Решение C0 | Обоснование | Альтернатива |
|---|---|---|---|
| C0-1 | Ресурс виден, но роли или авторства не хватает → **`403 forbidden`**; ресурс не виден → `404 not_found` | Участник уже знает о существовании ресурса: 404 ничего не скрывает, а UI не может объяснить отказ. Issue #7 оставляет «403-or-404» | Addendum 1 (T2, T4): 404 и для viewer. Тогда `forbidden` уходит из каталога, тесты T2/T4 ожидают 404 |
| C0-2 | Состав путей уточнён: добавлены `GET /v2/orgs`, `GET /v2/auth/csrf`, `/v2/projects/{p}/brand*`, `GET /v2/threads/{t}/messages`, `GET /v2/threads/{t}/requests/{request_key}`, `GET /v2/messages/{m}/result`; `GET /v2/threads/{t}` больше не возвращает сообщения | Отдельные контракты для списка организаций, бренда, истории и результата; восстановление по ключу невозможно без поиска по `request_key`, когда ответ `POST` потерян и `message_id` неизвестен | Таблица Addendum 1 как есть |
| C0-3 | Optimistic concurrency через целочисленный `version` / `expected_version` у проекта и у бренда; код `409 stale_project` | Addendum 2 вводит `project_brands.version`; единый механизм для обоих ресурсов | `expected_updated_at` (Addendum 1) или `If-Match` / ETag |
| C0-4 | `message` обязан совпадать во всех ревизиях одного `request_key` (иначе `409 revision_conflict`) | Сохранённая интерпретация ядра привязана к `(owner, request_key, fingerprint сообщения)`; смена текста — новая задача и новый ключ. Это строже ядра | Разрешить смену текста (ядро примет, но заново вызовет интерпретацию) |
| C0-5 | Принятый запрос хранится целиком и отдаётся как `UserMessage.input` всем участникам с доступом к треду | Нужен для безопасного повтора тем же payload и для ответа на уточнение с другого устройства; отправленное в проектный тред — проектный материал. Новая колонка в `thread_messages` | Отдавать `input` только автору; остальные видят только `text` |
| C0-6 | `next_action` вычисляет сервер; состояние «сохранено, но не принято ядром» — это `pending` + `resubmit_same_key` | Клиент не дублирует автомат состояний; отдельное состояние `not_started` не нужно | Отдельное значение `not_started` в `ExecutionState` |
| C0-7 | `ambiguous` — долговременное **состояние** (HTTP 200); `503` означает «исход ещё не определён». Нужен read-only `peek` receipt в ядре либо вывод по времени | Через публичные методы `ExecutionStore` состояния `running` и `ambiguous` неразличимы | Всегда `503` до ручного разбора |
| C0-8 | `expired` покрывает и «receipt истёк до материализации», и «запрос не был принят в окне admission» (`state_reason`); во втором случае ключ закрывается web-слоем и слот треда освобождается | Иначе сообщение, потерявшее клиентский payload, навсегда блокирует тред | Отдельное состояние `abandoned` |
| C0-9 | Один выполняющийся запрос на тред уже для Copilot-тредов (`409 thread_busy`) | Требование issue #7; та же механика нужна веб-чату. Параллельная работа — в другом треде | Сериализация только для chat-тредов |
| C0-10 | CSRF: привязанный к сессии токен выдаётся в теле (`AuthSession`, `GET /v2/auth/csrf`) и передаётся в `X-CSRF-Token` | Клиентский контракт не зависит от чтения cookie; аудит предлагал double-submit cookie — сервер может добавить его как реализационную деталь | Только double-submit из не-HttpOnly cookie |
| C0-11 | Необязательный `Idempotency-Key` на создании проекта и треда | Повтор после потерянного ответа не создаёт дубликат | Без ключа; дубликаты удаляет пользователь |
| C0-12 | Наставник в C0 читается из ядра делегированно и в `result_snapshots` не материализуется | Данные наставника в ядре не истекают; `result_snapshots.message_id UNIQUE` не вмещает второй snapshot | Материализовать `case_mentor.v1` (нужна правка уникальности) — решить в B8 |
| C0-13 | `UNSUPPORTED` хранится как payload `web_api.v2` без текста: только `reason` | Текст и подсказки — дело UI и локализации; snapshot остаётся честным и после включения чата | Хранить текст сообщения в snapshot |
| C0-14 | В `UserRef` отдаётся целочисленный `users.id` и `display_name` | Простая ссылка на автора внутри тенанта; Telegram ID и email не отдаются | Непрозрачный публичный идентификатор пользователя (новая колонка) |
| C0-15 | Тело ошибки без текстового сообщения; добавлен `request_id` | Нет эха ввода и нелокализованных строк; есть идентификатор для поддержки | Поле `message` для разработчиков |
| C0-16 | HTTP-коды snapshot-ошибок: `409 result_format_unsupported`, `503 result_corrupted`, `503 result_unreadable`, `410 result_gone` | Разделение повреждения, несовместимости формата и дефекта кода | Иные статусы при сохранении тех же `code` |
| C0-17 | `ProjectBrand.extra` — закрытый allowlist; `product_truth` и другие бизнес-поля попадают в ядро как brand-слой | Так уже работает существующий `brand_entries`; произвольный `extra_json` не принимается | Убрать бизнес-поля из бренда, оставить только в запросе |
| C0-18 | Список legacy-истории не отдаёт `source_id` и `capabilities`; детали элемента отложены (`deferred`) | `capabilities` описывают Telegram-поток; результат элемента в backend не типизирован | Типизировать в C0 (означало бы выдумать схему) |
| C0-19 | `execution_invalid` и `stale_context` не входят в коды `/v2` | Первый превращается в состояние `ambiguous`, второй относится к контексту Telegram-чата | Пробрасывать коды ядра как есть |
| C0-20 | Companion-эндпоинт бота `/internal/identity/web-login-link` описан в README, а не в OpenAPI | Другая trust-зона; не должен попадать в сгенерированный браузерный клиент | Отдельный OpenAPI-файл для internal-зоны |

## 5. Что C0 не утверждает

- Наличие какого-либо маршрута `/v2`, таблицы или флага в backend сегодня.
- Exactly-once исполнение внешней модели.
- Линеаризуемый отзыв доступа.
- Бессрочное хранение истории и полное удаление данных.
- Работающие upload, документы, изображения, биллинг и командные организации.
