# B2.0 — контракт браузерной сессии Brenvio

**Утверждено владельцем 21 ноября 2026 для internal beta.** B1a интегрирован в master через #220. Контракт развивает Web API v2 на e68621c и заменяет проект #217 для CSRF, browser confirmation, DTO и флагов. Публичный challenge и exchange описаны в [OpenAPI](web-api-v2.openapi.yaml), закрытое подтверждение — в [bot-only OpenAPI](telegram-confirm.internal.openapi.yaml).

## Публичные маршруты

| Маршрут | Контракт и проверяемый результат |
|---|---|
| POST /v2/auth/telegram/challenge | JSON {token}, same-origin, ответ 200 TelegramBrowserChallenge и временная host-only cookie. Полный переход описан ниже. |
| POST /v2/auth/telegram/exchange | JSON с единственным полем token. До обработки ссылки проверить same-origin, затем подтверждение именно этой браузерной попытки (раздел о подтверждении ниже). Session CSRF для exchange не требуется. Одной транзакцией погасить ссылку, отозвать прежнюю сессию браузера при наличии и создать новую для users.id из проверенной identity. Только после commit выдать cookie. Успех — 200 AuthSession. Просроченная, погашенная и неизвестная ссылки дают одинаковый 401 login_token_invalid. Ошибка записи откатывает транзакцию целиком. |
| GET /v2/auth/csrf | Действующая cookie даёт 200 CsrfToken. Возвращает текущий токен при перезагрузке страницы и в другой вкладке той же сессии. Истёкшая или отозванная сессия даёт 401. |
| POST /v2/auth/logout | Проверить same-origin. Действующая сессия требует корректный CSRF. При ошибке — 403 без отзыва. При успехе — отзыв, 204 с пустым телом и удаление cookie. Вызов в допустимом origin без действующей сессии также возвращает 204 и очищает cookie. Завершение сессии не отменяет графы или jobs. |
| GET /v2/me | Principal берётся из cookie. 200 Me с действующей сессией, иначе 401. Включить только разрешённые поля. Telegram ID, provider subject, cookie и внутренний session ID не входят в DTO. |

Все ответы /v2, в том числе 204 и ошибки, получают Cache-Control private, no-store. У __Host-brenvio_session обязательны HttpOnly, Secure, SameSite=Lax и Path=/, атрибут Domain отсутствует. Удаление использует те же атрибуты и Max-Age=0. Заголовки доверенного бота действуют только во внутренней зоне. При ошибке хранилища вернуть 503, сохранив отличие от успешно выполненного logout.

## Сессия, CSRF и origin

Cookie содержит 32 случайных байта в base64url. В БД хранится SHA-256 секрета. После проверки сессии сервер вычисляет base64url без padding от HMAC-SHA-256. Ключ — отдельный случайный серверный секрет длиной не менее 32 байт, общий для обслуживающих экземпляров. Сообщение — ASCII-префикс `brenvio/web-csrf/v1`, один нулевой байт и 32 байта SHA-256 текущей session-cookie. Новая независимая cookie задаёт поколение сессии. Секрет поступает из server-side secret store. При плановой смене ключа отозвать сессии или удерживать ключ поколения до их завершения. Сравнение с X-CSRF-Token выполняется за постоянное время. GET csrf возвращает одно значение во всех вкладках. Хранение на клиенте только в памяти. Колонка csrf_hash из #217 не требуется.

Idle TTL — 7 дней, absolute TTL — 30 дней с выдачи. Каждый защищённый запрос проверяет хэш cookie, revoked_at и оба срока по серверному времени. Срок истёк при now >= expires_at. Обновление активности условное, сериализуется с отзывом и продлевает idle максимум до absolute. Отзыв предыдущей cookie при exchange действует и при смене аккаунта. Иные браузеры сохраняют свои сессии. Хранилище недоступно — 503, выдача запрещена.

WEB_APP_ORIGIN задаёт один канонический HTTPS origin (scheme, host, effective port), без credentials, пути, query, fragment и wildcard. Некорректное или пустое значение блокирует включение production auth. Ссылки строятся только из конфигурации. На unsafe methods проверять Origin целиком. При отсутствии Origin допустим только явный Sec-Fetch-Site: same-origin. Null, чужой Origin, противоречащие заголовки и отсутствие обоих признаков дают 403 csrf_failed до изменения состояния. Credentialed CORS выключен. При действующей сессии unsafe-операции требуют также CSRF, кроме специально описанных pre-auth challenge и exchange. Эти два запроса проверяют origin и не предоставляют доступ к данным через текущую cookie.

## Вход из браузера и подтверждение через Telegram

1. Бот в личном чате вызывает закрытый POST /internal/identity/web-login-link с проверенным actor. Backend разрешает Telegram identity через B1a в users.id. Без identity возвращает 409 telegram_identity_required. Таблица auth_tokens зарезервирована для Telegram web login. При выдаче сохраняются user_id, SHA-256 случайного 256-битного токена и срок 10 минут. Лимит выдачи — пять ссылок на пользователя за десять минут, подсчёт и вставка под одной блокировкой владельца. Бот отправляет URL с токеном во fragment.
2. После явного действия пользователя страница считывает fragment, очищает URL через history.replaceState и вызывает POST /v2/auth/telegram/challenge с тем же JSON {token}. GET страницы ничего не запускает. Для каждой новой ссылки требуется подтверждение, в том числе в уже знакомом браузере. Под блокировкой живой строки auth_tokens создаётся одна запись browser_attempts с PK/FK на токен: хэш случайного 256-битного секрета браузера и хэш отдельного случайного 128-битного кода подтверждения. Срок попытки ограничен исходным expires_at. Ответ 200 содержит код для отправки боту и устанавливает временную __Host-brenvio_attempt с Secure, HttpOnly, SameSite=Lax, Path=/ и остаточным TTL. Смена браузера или потеря ответа требует свежей ссылки. Повторный challenge не перезаписывает первую попытку.
3. Пользователь отправляет показанную в своём браузере команду с кодом в личный чат бота. Бот принимает её только от пользователя Telegram и вызывает POST /internal/identity/web-login-confirm с телом {confirmation_code} и удостоверенным actor. Одним условным изменением сервер ставит confirmed_at только для этого кода, текущего владельца verified identity и живой непогашенной попытки. Бот сообщает об успехе пользователю. Простое открытие ссылки, чужой actor или сообщение в группе не подтверждают попытку. Код из чужой вкладки не предлагается подтвердить push-кнопкой.
4. После подтверждения пользователь нажимает «Войти» в той же вкладке. Exchange сохраняет тело {token}. Одна транзакция проверяет хэши ссылки и attempt-cookie в этой таблице, confirmed_at, expires_at и consumed_at, условно погашает токен, отзывает сессию, указанную прежней session-cookie браузера, и создаёт новую. Только победитель обновления получает сессию после commit. До подтверждения, после истечения, при несовпадении cookie или повторе — одинаковый 401 login_token_invalid, без расходования ещё пригодной попытки. Успех очищает attempt-cookie. После потери ответа клиент проверяет /me и ожидаемый аккаунт, при неопределённости начинает новый вход. Для internal beta эта транзакция также должна завершить предусмотренный ниже onboarding.
5. Пересылка одной ссылки позволяет занять попытку до владельца, но получатель без подтверждения исходного Telegram-аккаунта не получает cookie сессии. Владелец запрашивает новую ссылку. Применять ограничение частоты challenge/exchange на доверенном edge и подтверждений по actor, возвращать 429 rate_limited с Retry-After. Login page без аналитики и сторонних скриптов. Не сохранять в логах URL бота, тела этих запросов, команды подтверждения, Cookie, Set-Cookie и CSRF; это относится также к proxy, traces и обработчикам ошибок.

## Флаги и HTTP-контракт

Оба флага по умолчанию выключены. WEB_AUTH_ENABLED из #217 заменяется двумя флагами из OpenAPI. Бот показывает кнопку при эффективном разрешении входа. Закрытие выдачи действует также на ранее выпущенные ссылки и подтверждения.

| WEB_API_ENABLED | WEB_TELEGRAM_LOGIN_ENABLED | Кнопка / выдача / challenge / confirm / exchange | GET csrf | POST logout | GET /v2/me |
|---|---|---|---|---|---|
| 0 | 0 | скрыта, выдача и confirm закрыты, public routes 404 | 404 | 404 | 404 |
| 0 | 1 | как при 0/0 | 404 | 404 | 404 |
| 1 | 0 | скрыта, операции закрыты с 403 feature_disabled | 200 / 401 | 204 / 403 | 200 / 401 |
| 1 | 1 | включены | 200 / 401 | 204 / 403 | 200 / 401 |

При API=0 внутренние операции входа возвращают 403 feature_disabled. При работающем API сохраняются обычные ошибки схемы, origin, лимитов и хранилища. Для штатного отключения сначала выключить Telegram login, оставить csrf/logout доступными, дождаться истечения или отозвать все оставшиеся сессии, затем закрыть API. При экстренном закрытии API отозвать оставшиеся сессии до повторного открытия.

AuthSession содержит schema_version=web_api.v2, csrf_token и me. CsrfToken содержит schema_version и csrf_token. Me содержит schema_version, user, identities, memberships, session и features. Для display_name использовать first_name, затем username, иначе null. SessionInfo содержит issued_at, idle_expires_at и absolute_expires_at. Все восемь обязательных полей Features вычисляет сервер. Только активные memberships. В /v2 явные bot credentials, включая сочетание с cookie, отклоняются, actor из запроса никогда не определяет владельца. Для защищённых маршрутов — 401 unauthenticated. Анонимный logout с корректным origin остаётся идемпотентным.

**Состояния попытки.** issued → pending после первого challenge → confirmed после команды от владельца → consumed после commit exchange. Срок ссылки ограничивает каждый переход. Повтор подтверждения возвращает 401 login_token_invalid. Один token_id имеет максимум одну попытку. До подтверждения по команде браузер не может получить сессию. Ограничение выдачи действует на пользователя, включая уже погашенные ссылки. Публичные лимиты применять по доверенному адресу источника до обращения к хранилищу. Ошибки случайных клиентов не расходуют бюджет выдачи ссылок владельца. Восстановление после чужого первого challenge — новая ссылка в личном чате.

Успешный challenge возвращает TelegramBrowserChallenge. Exchange сохраняет исходные TelegramExchangeRequest и AuthSession. Внутренний confirm имеет отдельный контракт, недоступный из публичного edge и SDK.

## Обязательные проверки перед включением

- PostgreSQL: 0015 → 0016 на данных, изоляция двух владельцев, один победитель при конкурентном challenge/exchange, rollback при сбое после погашения, гонка logout с продлением, точные границы idle/absolute и 10 минут.
- Два браузера и две вкладки: GET csrf в B сохраняет запрос A, ротация отвергает старую cookie и CSRF, logout отзывает обе вкладки. Пересланная ссылка без Telegram-подтверждения, подмена challenge, другой actor, другая attempt-cookie и повтор подтверждения не создают сессии.
- HTTP и edge: неверный, null, отсутствующий и противоречивый Origin/Fetch Metadata, отсутствие CSRF, смешанные bot/browser credentials, flags 00/01/10/11, лимиты и отказ БД. Проверить установку и удаление cookies, отсутствие секретов в открытом виде в БД/логах/storage, private, no-store на всех ответах, включая 204, 4xx, 503 и edge 404.
- Валидировать AuthSession, CsrfToken, Me и ошибки по OpenAPI. Проверить, что первый вход возвращает реальное членство и повтор входа не дублирует проект или импорт. Проверить недоступность internal routes извне и отказ production startup/rollout с включённой авторизацией при неверном HTTPS origin.

Условия начала B2.1 выполнены. Для публичной beta обязателен gate изоляции #219. Решение о production 0015 принимается отдельно.
